# Codebase refactor (2026-11-12)

## Context
Lingo grew quickly through phases 1–2 and M9 (~26k source lines, ~31k test lines, ~2.4k doc lines). The user wants the whole codebase made simpler without changing behaviour: delete dead code, organise directories, share duplicated logic, keep comments super succinct (decisions and non-obvious facts only), move what can be unit/browser-tested out of E2E so E2E stays light, and trim stale or overgrown docs so they pollute the context less. The tests are thorough, so simplify boldly.

The user also wants stronger static checks, and formatting that happens automatically from now on (a pre-commit hook).

The work runs as **9 phases, one fresh subagent each**, to keep every context clean. Each phase is its own branch and PR, merged before the next starts. Every phase reads this file and ticks itself off below. Phase 9 deletes it.

User decisions (2026-11-12):
- Delete completed plan files; git history keeps them.
- Merge the Dexie versions 1–4 into one. The user resets the check build's DB once (export first, then import).
- Remove future-only code: the `SyncBackend` interface, unused `BrowserEnv` fields (`syncDelayHint`, `extensionsPage`, `features.highlightUnderline` and the `supportsHighlightUnderline` stub), and the messages nobody sends (`getBrowserEnv`, `listTerms`).
- Merge i18n keys that hold the same English text (status words, language names, …).

## Rules for every phase
- **Behaviour stays the same.** Delete a test only if the same behaviour is tested elsewhere, and name that test in the PR body. Moved tests must fail first when the code is broken (break it on purpose once).
- **Comments**: keep only decisions, constraints and facts the code cannot show (browser quirks, site behaviour, data limits, user decisions with dates). Delete comments that restate a name or the code, section markers, and JSDoc on obvious members. Fix wrong or stale ones ("end card", "Phase 2", "refined in M5").
- Any export not imported outside its file loses `export`, unless a test needs it.
- Docs touched by a phase are updated in the same PR (paths in the spec's architecture section, `testing.md`, `development.md`, `status.md`).
- Flow: `git fetch origin main && git checkout -b refactor/<phase> origin/main` → work (run only the touched tests while iterating) → `npm run verify` passes → commit (English, no Claude attribution) → push → draft PR → `gh pr ready` → `~/.claude/scripts/merge-when-green.sh <n>` in the foreground → report.
- A UI-touching phase (8) renders the popup, settings and word list (and the article/video UI if touched) before and after, and checks they still match the mock.
- If a phase grows too big, split it (e.g. 7a/7b) and record the split in the plan doc.
- **Chaining**: the parent session runs each phase as one subagent, in order. The subagent does the whole phase, including ticking it here in its own PR and the merge (`~/.claude/scripts/merge-when-green.sh <n>` in the foreground, again after a timeout; fix, verify and push if CI fails), and returns a short report ending `PHASE N MERGED: PR #n` (or `PHASE N BLOCKED: <reason>`). The parent checks the merge and launches the next phase. Phase sessions and subagents never start sessions or scheduled tasks.
